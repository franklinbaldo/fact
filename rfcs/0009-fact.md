# RFC 0009: FACT — FACT Anchors Contexts and Types

## Summary

**FACT** is a recursive acronym: **FACT Anchors Contexts and Types**.

FACT separates a context into two planes:

- the **fact plane** is the semantic corpus: in-scope UTF-8 Markdown documents
  with YAML frontmatter, outside `.fact/`;
- the **control plane** is `.fact/`: context configuration, type specifications,
  validation policy, adapters, caches, and other machinery used to interpret the
  fact plane.

Markdown with YAML frontmatter is preferred in both planes whenever it naturally
fits. A Markdown document does **not** become a fact merely because it is
Markdown: anything under `.fact/` is configuration/control material and is
excluded from the fact set by definition.

A context may also carry CSV, JSON, source code, images, PDFs, archives, generated
artifacts, and other files. Outside `.fact/`, those files are resources rather
than facts. They enter the semantic model only through references from facts or
through an explicitly invoked adapter.

A native context is marked by `.fact/` and configured by `.fact/context.md`.
Every canonical fact carries a stable authored `id` and a `type`. A locally owned
`type` normally points to a specification under `.fact/specs/`, for example
`.fact/specs/Procedure.md`.

FACT is an independent specification. OKF and `franklinbaldo/okf-parser` are
sources of prior art and implementation evidence, not normative dependencies.

## Motivation

### Fact membership is not file membership

A context is a filesystem boundary, but a filesystem is not itself a semantic
model.

```text
context/
  .fact/
    context.md
    specs/Procedure.md
  procedures/onboarding.md
  data/accounts.csv
```

`procedures/onboarding.md` can be a FACT fact. `data/accounts.csv` is a resource.
`.fact/context.md` and `.fact/specs/Procedure.md` configure how the context is
understood. Only the first belongs to the fact plane.

This makes repository mixing predictable: by default, compose the fact plane.
Do not implicitly turn every file in every repository into knowledge.

### `.fact/` is infrastructure, not domain knowledge

Dot-directories are a familiar way to attach behavior and configuration to a
filesystem tree without confusing that machinery with the tree's ordinary
content. Git's `.git/` is the obvious analogy.

FACT uses `.fact/` for the same kind of separation. Reserved paths are acceptable
inside the control plane because they are infrastructure. The rule that ordinary
filenames do not secretly become domain semantics still applies to the fact
plane.

### Markdown first does not mean Markdown only

A separate YAML, JSON, or TOML file should not be introduced merely because it is
a convenient way to spell configuration. Human-authored configuration and specs
SHOULD use Markdown with YAML frontmatter when that is expressive enough.

Some control artifacts have an intrinsically useful syntax of their own: ignore
patterns, SQL declarations, binary caches, generated indexes, and similar files.
Those may live under `.fact/` without becoming a second fact format.

### Types should explain themselves

A bare label is readable but underspecified:

```yaml
type: Procedure
```

Canonical local FACT instead anchors a type to a specification that travels with
the context:

```yaml
type: .fact/specs/Procedure.md
```

The specification is a control document, not another fact. This removes any need
for a self-typed `TypeSpecification` bootstrap.

### Composition must preserve ownership

Vendoring or nesting one context inside another should expose more knowledge
without rewriting the meaning of the inner context. Filesystem containment,
visibility, ownership, context identity, fact identity, and resource membership
are therefore distinct concepts.

## Principles

### Markdown + frontmatter is the preferred authored surface

Canonical FACT facts are Markdown with YAML frontmatter. Human-authored control
documents SHOULD use the same surface when possible. Specialized control syntax
is permitted where it buys a real capability rather than merely duplicating
frontmatter in another serialization.

### The control plane never pollutes the fact plane

`.fact/` and everything below it are excluded from the fact relation by
definition. A type specification may be rich Markdown and still remain
configuration rather than a fact.

### Complete dogfooding

The repository that specifies FACT is itself a native FACT context. Every
normative mechanism that can be exercised deterministically here SHOULD be
exercised by the pull-request gate.

### Local first

A self-contained context should explain itself offline. Local specs and local
resources therefore resolve without a network. Network dereferencing may enrich a
context but is never required merely to establish native conformance.

### Many readers, one writer

Readers may inspect or adapt foreign forms. Canonical authored FACT remains one
thing: Markdown facts plus the `.fact/` control plane. Adapters do not redefine
what the canonical writer emits.

## Decision

### 1. `.fact/` marks the native context boundary

A directory containing `.fact/` is a native FACT context. Nested `.fact/`
directories create nested contexts.

The nearest native context boundary owns each ordinary file beneath it. Opening a
larger ancestor context may make nested facts visible, but it does not change
their owner.

### 2. `.fact/` is a control plane and never part of the fact set

All files below `.fact/` are control material: configuration, specifications,
policy, adapters, caches, generated metadata, or implementation artifacts.

Markdown remains preferred for authored control material, but location is
load-bearing: `.fact/specs/Procedure.md` is a Markdown type specification and is
**not** a FACT fact.

This rule is unconditional. Ignore files do not need to exclude `.fact/`, and a
repository mixer must not accidentally ingest `.fact/*.md` as semantic facts.

### 3. `.fact/context.md` configures stable context identity

The conventional and canonical context control document is:

```text
.fact/context.md
```

It uses YAML frontmatter. At minimum it declares a stable `id`; it SHOULD identify
its control specification through `type`:

```yaml
---
id: urn:fact:context:example
type: .fact/specs/Context.md
title: Example
---
```

The context `id` is authored identity. It is not recomputed from the directory
path, Git remote, repository URL, hostname, or checkout location.

`context.md` is configuration, not a fact, so its id does not compete with fact
ids and it does not appear in the fact relation.

### 4. The fact plane is in-scope Markdown outside `.fact/`

Every canonical fact is an in-scope `.md` document outside `.fact/` with YAML
frontmatter containing at least:

```yaml
id: onboarding
type: .fact/specs/Procedure.md
```

Within one owning context, fact ids MUST be unique. A file move MUST NOT by itself
change the authored id.

The stable key for a fact in a composed surface is therefore:

```text
(context_id, fact_id)
```

A permissive reader MAY inspect Markdown without canonical frontmatter or other
foreign inputs, but that does not silently make them canonical FACT facts.

### 5. `.fact/ignore` controls fact-plane scope

When present, `.fact/ignore` uses the proven ignore model implemented by
`okf-parser`: gitignore-style matching, including negation and last-match-wins.
Patterns are relative to the context root. `!` re-includes a path.

FACT keeps the useful deviation already exercised in `okf-parser`: a negation MAY
re-include a path beneath an excluded parent rather than becoming ineffective
because a filesystem walk was pruned too early.

`.fact/` itself remains excluded by definition and cannot be re-included into the
fact plane.

### 6. Non-Markdown ordinary files are resources

A context may carry any files outside `.fact/`. Non-Markdown files are opaque
resources to the FACT core.

A fact can give a resource semantic meaning through a Markdown link, a frontmatter
field such as `resource`, or a type-specific reference. Relative resource paths
resolve from the fact document unless the type specification says otherwise.

A resource does not become a fact merely because an adapter can parse it. An
adapter may produce a structured view; canonical facts exist only when a writer
explicitly materializes Markdown facts.

For corpus composition and repository mixing, the default semantic input is the
fact plane. Resource following is explicit.

### 7. Local type specifications live under `.fact/specs/`

A canonical local type reference points from a fact to a control document:

```yaml
type: .fact/specs/Procedure.md
```

A type specification SHOULD itself be Markdown with YAML frontmatter. The
recommended minimum is:

```yaml
---
kind: type-spec
name: Procedure
---
```

Because the specification lives under `.fact/`, it is not required to carry a
fact `id` or a fact `type`, and no recursive `TypeSpecification` bootstrap is
needed.

A genuinely external type specification may use an absolute URI. Network access
is not required for native local types.

### 8. Context composition is visibility, not inheritance

An outer context may expose or query facts owned by an inner context. It MUST NOT
silently rewrite the inner context's ids, type resolution, ignore policy,
validation policy, or adapter configuration.

Normative interpretation is vantage-invariant: opening a larger tree may reveal
more neighbours but does not change what an already valid inner fact means.

Explicit import or policy-sharing mechanisms may be standardized later; lexical
shadowing by directory position is not such a mechanism.

### 9. Links keep ordinary Markdown semantics

Relative Markdown links resolve from the document carrying the link. Absolute
URIs remain absolute. Context-root-specific references may be defined by a type
specification or control convention where necessary.

Stable identity and referential integrity are distinct. Moving a fact can preserve
its `id` while breaking an old path link.

### 10. `.fact/` may host specialized control resources when they earn their syntax

Markdown/frontmatter is the default for authored configuration, but FACT does not
force intrinsically structured executable or pattern languages into Markdown.
Examples of legitimate control resources include:

```text
.fact/
  context.md
  ignore
  specs/<name>.md
  specs/<name>.schema.sql
  schema.sql
  adapters/
  cache/
```

The existence of these paths does not automatically make every one normative.
Individual conventions define their own semantics.

### 11. Relational declarations are an opinionated optional control convention

`okf-parser` has already demonstrated two useful extensions beyond the small OKF
core:

- a physical declaration beside a type specification;
- a context-wide relational contract for keys and cross-type references.

FACT adopts their **control-plane locations** as the preferred convention:

```text
.fact/specs/Procedure.schema.sql   # optional per-type physical declaration
.fact/schema.sql                   # optional context-wide relational contract
```

These files are not facts. SQL is used here because the declaration is genuinely
relational/executable, not because FACT prefers SQL over Markdown for ordinary
metadata.

Execution of authored SQL is a trust boundary. A generic FACT reader need not
execute these files to enumerate facts or resolve local type specs. A tool that
chooses to execute them MUST make that capability explicit.

The initial relational contract recognizes the useful semantics already proven in
`okf-parser`: physical column intent per type and context-level `PRIMARY KEY`,
`UNIQUE`, and `FOREIGN KEY` relationships. Independent implementations may expose
the same semantics without using DuckDB internally.

### 12. Canonical mutation tooling is preview-first and staged

The file format does not require one CLI, but canonical writers SHOULD preserve
the safety properties already exercised by `okf-parser` relational writes:

1. preview the intended change without committing by default;
2. stage a complete candidate tree;
3. validate the candidate before replacing authored files;
4. detect conflicting concurrent edits when practical;
5. preserve unrelated frontmatter and Markdown content round-trip;
6. refuse a lossy rewrite rather than silently normalizing away information;
7. commit atomically when the platform permits it.

Protocol adapters such as MCP SHOULD expose preview and commit as distinct effects
when the protocol has static effect metadata. That is a tooling convention, not a
second file-format serialization.

### 13. Diagnostics are graded

FACT distinguishes inability to interpret from non-canonical-but-recoverable
input:

| level   | meaning                                                               |
| ------- | --------------------------------------------------------------------- |
| `error` | authored meaning is ambiguous, contradictory, or unreadable           |
| `warn`  | usable input, but intended meaning cannot be recovered reliably        |
| `info`  | meaning is recoverable, but authored form is not canonical FACT        |
| `hint`  | canonical FACT with a non-semantic improvement available              |

Identity collisions and missing required local type specs are errors. Bare type
labels may be recoverable input without becoming canonical output.

### 14. Foreign formats cross an adapter boundary

Vocabulary mapping, structural adaptation, resource parsing, and projection to a
foreign validator are distinct jobs. They belong behind explicit adapters.

Supporting OKF, JSON records, wikilinks, CSV rows, or another dialect does not add
a second canonical FACT writer.

### 15. Canonical FACT remains small

Understanding the core fact plane requires no database, graph engine, package
manager, web service, schema registry, or network connection.

Canonical facts are Markdown with YAML frontmatter. The `.fact/` control plane
anchors how those facts are interpreted. Specialized control resources are
optional capabilities, not alternative fact serializations.

## Native conformance

A native context is canonical FACT when all of the following hold:

1. `.fact/` exists and contains a parseable `.fact/context.md` with a stable
   non-empty context `id`.
2. No file under `.fact/` appears in the semantic fact set.
3. Every in-scope fact is Markdown outside `.fact/` with non-empty stable `id`
   and `type` frontmatter.
4. Fact ids are unique within the owning context.
5. Every canonical local `type` reference resolves from the owning context root
   to a control document under `.fact/specs/`.
6. A local type specification is valid control material; it is not required to
   satisfy fact identity or typing rules.
7. If `.fact/ignore` exists, scope follows its normative ignore semantics.
8. Opening an outer context does not change the normative interpretation of an
   inner context.
9. Non-Markdown ordinary files do not enter the fact set merely by existing.

A reader may accept non-canonical or foreign input. Acceptance is not native
conformance.

## Complete dogfooding gate

This repository is an executable fixture for the native rules above. Every pull
request MUST run a deterministic gate that checks, at minimum:

- the repository root and at least one nested context have `.fact/` boundaries;
- `.fact/context.md` supplies stable context identity;
- Markdown control documents under `.fact/` are never counted as facts;
- every in-scope fact has stable `id` and local `type` resolution;
- type specifications resolve as control documents;
- fact ids are unique per owning context;
- relative Markdown links used by the fixture resolve;
- at least one referenced non-Markdown resource resolves while remaining outside
  the fact set;
- the repository does not regress to YAML sidecars for configuration that is
  naturally represented by Markdown/frontmatter.

A documentation-only change is not exempt.

## Proven conventions inherited as design evidence

`franklinbaldo/okf-parser` has accumulated several extensions beyond baseline
OKF through real use. FACT treats those accepted experiments as evidence:

| okf-parser convention | FACT direction |
| --- | --- |
| `.okfignore` with gitignore semantics | `.fact/ignore` control convention |
| `--require-spec` | local type specs are canonical, not caller configuration |
| per-type `.schema.sql` | `.fact/specs/<name>.schema.sql` optional relational control resource |
| bundle `okf.schema.sql` | `.fact/schema.sql` optional context relational contract |
| relational frontmatter `apply` | preview-first staged canonical mutation tooling |
| effect-aware MCP writes | tooling adapters declare effects; preview and commit stay distinct |

Parser packaging, language bindings, release automation, and other implementation
choices are not FACT format semantics merely because they exist in `okf-parser`.

## Inspirations

[Open Knowledge Format (OKF)](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)
inspired the use of Markdown with YAML frontmatter, producer-defined fields, and
a deliberately small knowledge core. FACT is not an OKF profile or superset.

`franklinbaldo/okf-parser` supplied implementation evidence for mixed-repository
scope, local specs, relational declarations, safe mutation, and effect-aware tool
surfaces. FACT adopts or adapts those ideas explicitly rather than inheriting the
parser as a dependency.

Git inspires the control-plane boundary: a small dot-directory can attach stable
behavior to a tree without making the tree's path its identity.

## Non-goals

- Claiming that a `fact` is objectively true.
- Treating `.fact/` configuration as semantic facts.
- Treating every file in a context as a fact.
- Establishing a global type or context registry.
- Requiring HTTP(S), DNS, or network access for native validation.
- Treating filesystem paths as stable identity.
- Flattening nested contexts into one namespace.
- Requiring DuckDB or SQL support for basic FACT reading.
- Making every foreign format round-trip losslessly through FACT.

## Open questions

- Recommended minting conventions for new context and fact ids.
- Minimal syntax for explicit cross-context imports, if needed.
- Which relational declaration details belong in this founding RFC versus a
  dedicated follow-up RFC.
- Which adapter contracts deserve shared conformance fixtures.
- Whether a canonical move operation should repair resolvable inbound links.
