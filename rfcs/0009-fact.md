# RFC 0009: FACT — FACT Anchors Contexts and Types

## Summary

**FACT** is a recursive acronym: **FACT Anchors Contexts and Types**.

FACT has one canonical semantic surface: **UTF-8 Markdown with YAML
frontmatter**. Facts, context anchors, type specifications, and other authored
knowledge use that same representation whenever the information can naturally be
expressed as FACT knowledge.

A context may physically contain other files — CSV, JSON, source code, images,
PDFs, archives, generated artifacts, and so on. FACT can list and carry those
files, but their presence does not make them facts. They are opaque resources by
default. A Markdown fact gives such a resource semantic meaning by referring to
it.

A native context is marked by `.fact/`. Its stable identity is carried by an
ordinary Markdown fact of type `.fact/specs/Context.md`; every fact carries a
stable authored `id`; and a canonical local `type` identifies the Markdown
specification that defines it, normally through a reference such as
`.fact/specs/Procedure.md`.

FACT is its own specification. It is not a profile, extension, or subset of
another knowledge format. Readers may support foreign inputs through adapters,
but adapters do not redefine what canonical FACT writes.

The word `fact` means an atom asserted *in a context*. It does not claim that the
atom is objectively true. An allegation, observation, hypothesis, rule, or
procedure can all be facts when a context records them as such.

## Motivation

Plain filesystems are excellent containers but poor semantic models. Several
questions remain implicit:

- Which files are semantic FACT knowledge, and which are merely resources?
- Which documents belong to one context rather than another?
- Does moving a document or context change its identity?
- What does an authored `type` actually mean?
- Can contexts compose without pretending they were authored in one namespace?
- How does a CSV, image, PDF, or source file participate without forcing FACT to
  invent a second native serialization?

FACT makes those answers explicit while keeping the canonical knowledge layer
small.

### Markdown is the semantic boundary

FACT deliberately does not interpret every file it encounters as a fact.
Filesystem membership and fact membership are different things.

For example:

```text
context/
  .fact/
  procedures/onboarding.md
  data/accounts.csv
```

`accounts.csv` is a file in the context. It may appear in a context file listing,
be copied with the context, and be opened by a tool. It does **not** enter the FACT
fact set merely because it exists there.

A Markdown fact can make the relationship explicit:

```yaml
---
id: resource:account-register
type: .fact/specs/Resource.md
resource: ../data/accounts.csv
---
```

The fact is semantic knowledge. The CSV is the referenced resource.

This gives repository mixing a predictable default: mix the FACT facts, not every
byte in every repository. A tool MAY follow or transform referenced resources
when the operation asks for them, but that is a second step rather than implicit
fact creation.

### Filenames should not secretly become domain semantics

Ordinary filenames do not define what a fact means. `README.md`, `index.md`,
`log.md`, an RFC, and a type specification may all be facts when in scope; their
meaning comes from frontmatter and content.

`.fact/` is intentionally structural: its presence marks a native context
boundary. Inside it, the context anchor is identified by its `type`, not by a
required filename. `.fact/context.md` is a useful convention, not the semantic
rule.

### Types should explain themselves

This is readable but underspecified:

```yaml
type: Procedure
```

A reader sees a label but not the specification that gives it meaning. Canonical
local FACT anchors the type to knowledge that travels with the context:

```yaml
type: .fact/specs/Procedure.md
```

An external specification may instead be identified by an absolute URI. Protocol
is not semantics, and network access is never required merely to open a
self-contained context.

### Composition must preserve meaning

Putting one knowledge tree inside another is useful for vendored knowledge,
multi-repository corpora, and federated queries. It should not silently rewrite
what the inner tree means. FACT therefore separates filesystem containment, file
membership, fact membership, visibility, ownership, and identity.

## Principles

### Markdown first

Whenever FACT can represent authored semantic information as Markdown with YAML
frontmatter, that is the canonical form. A separate YAML/JSON/TOML control file
should not be introduced merely because configuration syntax is convenient.

Other file formats remain legitimate resources. The distinction is not “Markdown
allowed, everything else forbidden”; it is “Markdown facts are the canonical
semantic interface, other files are opaque until facts refer to them or adapters
are explicitly invoked.”

### Complete dogfooding

The repository that specifies FACT is itself a canonical FACT context. Normative
native mechanisms are exercised here, not merely described here. A pull request
must fail if the repository stops satisfying its own rules.

The repository also contains a nested native example so composition, context
ownership, local type specifications, stable identities, ordinary Markdown
links, and referenced non-Markdown resources are exercised continuously.

### Independent implementation

FACT must remain implementable by someone who did not write the reference tools.
Conformance is defined by authored files and deterministic rules, not by hidden
state in one parser.

### Local first

A self-contained context should explain itself offline. Local specification
references are therefore the normal canonical form for locally owned types.
Absolute URIs are useful for genuinely external specifications, not a requirement
for a global registry.

### Many readers, one writer

Readers may recover useful information from foreign dialects or inspect
non-Markdown resources. The canonical writer has one job: emit FACT facts as
Markdown with YAML frontmatter. An adapter is a boundary, not a way to multiply
canonical FACT representations.

## Capabilities unlocked

The decisions below buy seven capabilities:

1. **A context describes itself.** Opening the tree is enough to discover its
   identity and type specifications.
2. **A fact's identity is independent of its location.** Moving a fact does not
   create another fact merely because its path changed.
3. **A context's identity is independent of its location.** Vendoring or moving a
   context does not create another owning context merely because its root moved.
4. **Types identify their specifications.** A reader can distinguish a display
   label from the knowledge that defines the label.
5. **Contexts compose without flattening ownership or semantics.** Outer contexts
   may see inner facts while the inner context keeps its own interpretation.
6. **Resources can travel with knowledge without becoming a second fact format.**
   CSV, JSON, images, PDFs, code, and other files remain resources until FACT
   facts refer to them.
7. **Foreign inputs do not multiply canonical forms.** Adapters may be numerous;
   canonical FACT remains singular.

## Decision

### 1. Every in-scope Markdown document is a fact

A context has no second class of in-scope Markdown documents. Every in-scope
`.md` file is parsed as a fact, including Markdown under `.fact/specs/`.

Canonical FACT facts have YAML frontmatter. At minimum they carry a non-empty
`id` and `type`.

Filesystem containment alone is not assertion. `.factignore`, when present, may
define exclusions from a context's scope. A nested native context is owned by its
own `.fact/` boundary rather than absorbed into the nearest outer context.

Ordinary filenames are not reserved as domain types.

### 2. Non-Markdown files are resources, not facts

A native context may contain files of any format. FACT implementations MAY expose
a file list for the context, including non-Markdown files, but the canonical fact
relation contains only in-scope Markdown facts.

A non-Markdown file is opaque to the FACT core. Its extension does not cause FACT
to parse it into rows, objects, images, text chunks, or facts.

A fact may refer to a resource through ordinary Markdown links, a frontmatter
field such as `resource`, or a type-specific field. Once referenced, a consumer
can expose or open that resource while preserving the distinction between the
fact that describes it and the bytes being described.

An adapter MAY interpret a resource structurally — for example, reading a CSV as
rows — but adapter output is not silently promoted into canonical authored FACT.
If canonical facts are created from that interpretation, a writer must explicitly
materialize them as Markdown with frontmatter.

For corpus composition and repository mixing, the default semantic input is the
fact set. Non-Markdown resources are ignored unless the operation explicitly
follows, includes, or adapts them.

### 3. `.fact/` marks a native context; a `Context` fact anchors its identity

A native FACT context contains a `.fact/` directory. Directly inside `.fact/`,
exactly one Markdown fact has the canonical local Context type:

```yaml
---
id: urn:fact:context:example
type: .fact/specs/Context.md
title: Example
---
```

The filename is not normative. `.fact/context.md` is the conventional spelling;
the `type` is what identifies the anchor.

The context anchor is an ordinary fact. Its authored `id` is also the stable
context identity. FACT therefore does not require `context.yaml` or another
second configuration serialization for context identity.

The context id is not recomputed from the directory path, repository URL,
hostname, or current checkout location. Moving or vendoring the context preserves
its identity.

Context ids need only be unambiguous in the composed surface that uses them. A
URI-shaped value is convenient but no URI scheme or registry is normative.

### 4. Facts carry stable authored ids

Canonical FACT facts contain a non-empty `id` in frontmatter:

```yaml
id: onboarding
```

The id survives a file move. Within one owning context, two in-scope facts MUST
NOT have the same id.

The stable relational key for a fact in a composed surface is:

```text
(context_id, fact_id)
```

A writer must never derive `fact_id` from the current path. An importer may mint
an id for foreign input, but once canonical FACT is written that id becomes
authored state.

Identity and referential integrity remain distinct: moving a fact may preserve
its id while breaking a path-based Markdown link to its old location.

### 5. Canonical `type` identifies a specification

Every canonical fact carries a non-empty `type`. When the type is owned by the
same context, the canonical spelling is a context-root-relative reference to its
specification:

```yaml
type: .fact/specs/Procedure.md
```

A genuinely external specification may use an absolute URI:

```yaml
type: https://example.org/specs/Procedure.md
```

Readers MAY accept a bare string such as `Procedure` as recoverable input, but a
canonical writer does not invent semantics for it. If a matching local
specification can be inferred, the input can be normalized with an advisory
diagnostic; otherwise the missing anchor is reported.

A relative `type` reference is resolved from the owning context root, not from
the fact's current directory. Moving the fact therefore does not change which
specification it names.

### 6. Type specifications are ordinary facts

Markdown documents below `.fact/specs/` are not metadata hidden from the model.
They are ordinary facts and therefore carry their own stable `id` and `type`.

The bootstrap type is `TypeSpecification`. Its specification may type itself:

```yaml
---
id: type:TypeSpecification
type: .fact/specs/TypeSpecification.md
title: Type Specification
---
```

This is a finite bootstrap, not an infinite regress. A reader needs only the
small FACT frontmatter contract to parse the document before following its type
reference.

### 7. Contexts compose without changing inner meaning

Nested `.fact/` directories create nested owning contexts. The nearest context
boundary owns a fact or resource.

An outer context may expose or query facts from an inner context, but it MUST NOT
silently change how the inner context resolves its own ids, type references,
aliases, or validation policy.

Composition is visibility, not inheritance. If one context imports vocabulary or
policy from another, that relationship must be explicit authored knowledge,
preferably as FACT facts rather than an unrelated control serialization.

Normative interpretation is therefore vantage-invariant: opening a larger tree
may reveal more neighbours, but it does not rewrite the meaning of facts already
valid in an inner context.

### 8. Links keep ordinary Markdown semantics

A relative Markdown link resolves from the document that carries it. A
context-root-anchored link resolves from the owning context root. Absolute URIs
remain absolute.

The same principle applies to relative file references in frontmatter unless a
type specification says otherwise: they are resolved relative to the fact that
carries them.

Path links intentionally remain path-dependent. Stable ids do not pretend that a
stale path is still a valid link. A future `fact mv` may move a file and rewrite
inbound links it can resolve, but that is a convenience layered on top of the
identity model.

A path that points outside a context is not inherently malformed; it simply has a
relocatability cost that tools may diagnose.

### 9. `.fact/` stays small and Markdown-first

The native control directory should contain semantic FACT knowledge whenever
possible:

```text
.fact/
  context.md                 # conventional filename; ordinary Context fact
  specs/<name>.md            # type specification facts
```

Additional policy, vocabulary, or adapter declarations SHOULD be represented as
Markdown facts with frontmatter when their semantics fit the FACT model.

Non-Markdown implementation artifacts may still exist where a different format
is intrinsically useful, but they are resources/configuration for tooling rather
than a competing canonical knowledge layer.

### 10. Network dereferencing is never normative

Resolving `.fact/specs/Procedure.md` is a local context operation and may be
required for canonical conformance.

Fetching an HTTP(S) type specification is different. A timeout, unavailable DNS,
authentication boundary, or remote 404 does not by itself make a context invalid.
Remote material may be cached as enrichment, but conformance cannot depend on the
network being available.

### 11. Diagnostics are graded

FACT distinguishes parseability from preference:

| level   | meaning                                                               |
| ------- | --------------------------------------------------------------------- |
| `error` | authored meaning is ambiguous, contradictory, or unreadable           |
| `warn`  | usable input, but intended meaning cannot be recovered reliably        |
| `info`  | meaning is recoverable, but authored form is not canonical FACT        |
| `hint`  | canonical FACT with a non-semantic improvement available              |

Examples:

| condition                                  | default |
| ------------------------------------------ | ------- |
| duplicate `id` inside one context          | error   |
| missing local type specification           | error   |
| multiple Context anchors in one context    | error   |
| bare `type` with an unambiguous local spec | info    |
| bare `type` with no specification known    | warn    |
| unreferenced non-Markdown file             | —       |
| unreachable external HTTP(S) specification | info    |

Rules that protect identity or remove ambiguity cannot be demoted below error.
Advisory policy may itself be represented as FACT knowledge rather than requiring
a dedicated YAML control file.

### 12. Type identity and relational naming are separate

A specification reference is a good semantic identifier and can be a poor table
or variable name. Relational surfaces may derive or explicitly declare a local
symbol such as `Procedure`, but MUST preserve the resolved type reference beside
that symbol.

Two distinct type specifications must never silently collapse onto the same local
symbol. A collision requires qualification or an explicit alias.

### 13. Foreign specifications and structured resources cross an adapter boundary

Compatibility with another format can mean different things:

- vocabulary aliasing;
- structural adaptation from another document shape;
- parsing a resource such as CSV or JSON into a structured view;
- projection to a foreign validator or serializer.

Those jobs belong at an explicit adapter boundary. Supporting a foreign dialect
or parsing a resource must not add a second canonical FACT writer.

### 14. Canonical FACT is Markdown plus YAML frontmatter

The canonical authored semantic representation is UTF-8 Markdown with YAML
frontmatter. At minimum a canonical fact has `id` and `type`; other fields are
producer vocabulary unless a referenced type specification constrains them.

Unknown frontmatter fields are preserved rather than rejected merely because the
core specification does not know them.

FACT intentionally does not require a database, graph engine, schema registry,
web service, package manager, or secondary configuration language to understand a
native context.

## Native conformance

A native context is canonical FACT when all of the following hold:

1. `.fact/` exists.
2. Exactly one direct Markdown fact inside `.fact/` has type
   `.fact/specs/Context.md`; its `id` is the stable context identity.
3. Every in-scope Markdown document belongs to exactly one nearest native context.
4. Every in-scope Markdown fact has a non-empty stable `id` and `type`.
5. Fact ids are unique within their owning context.
6. Every local type reference resolves from the owning context root.
7. Every local Markdown type specification is itself an ordinary conformant fact.
8. Opening an outer context does not change the normative interpretation of an
   inner context.
9. Non-Markdown files do not enter the canonical fact set merely by existing.

A reader may accept non-canonical or foreign inputs. Acceptance is not the same
thing as native conformance.

## Complete dogfooding gate

This repository is a normative executable fixture for the native rules above.
Every pull request MUST run a deterministic gate that checks, at minimum:

- the repository root is a native context anchored by a Markdown Context fact;
- every in-scope repository Markdown document is a canonical fact;
- all fact ids are unique in their owning contexts;
- all local `type` references resolve to specification facts;
- `TypeSpecification` exercises the finite self-typing bootstrap;
- at least one nested native context is present and independently valid;
- ordinary relative Markdown links used by the fixture resolve;
- at least one non-Markdown resource is referenced by a fact, resolves, and is
  not counted as a FACT fact.

A documentation-only change is not exempt. If the specification describes a
native invariant that this repository can exercise deterministically, the gate
should exercise it.

## Inspirations

FACT borrows good ideas from prior work without inheriting another format's
contract.

[Open Knowledge Format (OKF)](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)
inspired the choice to keep knowledge human-readable as Markdown with YAML
frontmatter, to tolerate producer-defined fields, and to keep the core small.
FACT is **not** an OKF profile or superset, and it makes no special compatibility
promise to OKF. Supporting OKF is an adapter concern on the same footing as any
other foreign dialect.

Git inspires the idea that a small marker directory can establish a portable
context boundary without making the filesystem path itself the identity.

## Non-goals

- Claiming that a `fact` is objectively true.
- Establishing a global type or context registry.
- Requiring HTTP(S), DNS, or network access for native validation.
- Treating filesystem paths as stable identity.
- Flattening nested contexts into one namespace.
- Treating every file in a context as a semantic fact.
- Defining a database, query engine, or UI as part of the file format.
- Making every foreign format round-trip losslessly through FACT.

## Open questions

- Recommended minting conventions for new context and fact ids.
- Minimal syntax for explicit cross-context imports, if they prove necessary.
- Whether policy/vocabulary facts need standard core types or can remain
  producer-defined until concrete use cases converge.
- Whether canonical writers should expose a standard move operation that repairs
  resolvable inbound links.
- Which adapter contracts deserve standard conformance fixtures once adapters are
  implemented.
